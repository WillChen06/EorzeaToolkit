# Foundation Models：道具搜尋解析評估

## 目標

在 Mac 上用 Apple 的裝置端模型，量出「一句繁中描述 → 道具搜尋條件」解析得多準，結果用來決定要不要做 App 的描述搜尋。
評估工具留在 repo 裡，每次 iOS 大版本換模型時，用同一份評估集重跑。

## 範圍（這個 Phase 只做這些）

- 解析程式碼，App 之後直接用同一份：
  - 解析結果的結構（見「解析結果」）；
  - 給模型的指示。模型只判斷用法、擷取關鍵字。
    指示用完整的「句子 → 結果」範例說明，不放會被照抄的單一數值或名稱，範例也不取自評估集；
  - 從原文比對其他條件的程式。分類、部位、職業的名稱從 `items.json` 和 App 的職業 filter 選項產生，不另外寫死一份；
  - 把名稱對回 id 的邏輯。
- 解析程式碼放在 App 的原始碼目錄，App target 和評估工具 target 一起編譯。
  - 用到 FoundationModels 的部分全部放在 iOS 26／macOS 26 的 availability 後面。
  - App 這個 Phase 不呼叫它。
- `project.yml` 新增 macOS 命令列 target（評估工具），最低 macOS 26。CI 不 build、也不跑這個 target。
- 評估集 `Tools/ItemQueryEval/cases.json`，組成見「評估集」。
- `scripts/run_item_query_eval.sh`：build 評估工具並執行。另有檢查模式，不呼叫模型，只檢查評估集。
- 結果記錄在 `docs/foundation-models-eval.md`。
- `AGENTS.md` 的 Commands 加上評估工具。

前置條件：CI 改用 Xcode 27.1（#77）。解析程式碼由 App target 一起編譯，CI 需要有 FoundationModels 的 SDK。

## 不在這個 Phase

- App 的描述搜尋入口、prewarm、各種狀態畫面，以及把解析結果套用到搜尋（AI Phase 1）。
- 道具說明文字、靠意思的查詢（例：能讓陸行鳥變色的東西）。
- Private Cloud Compute、tool calling、多輪對話。
- 手機上的延遲，只有實機量得準。
- 修改 filter 本身，裝備等級由 `prompts/item-equip-level.md` 處理。

## 解析結果

每句話解析成下列欄位，沒提到的欄位留空。

模型只判斷用法、擷取關鍵字，其他條件由程式從原文比對。
前兩輪評估由模型挑選條件，正確率遠低於門檻（見 `docs/foundation-models-eval.md`）；程式比對的結果固定，也寫得了 unit test。

- 用法是「無法處理」時，其他欄位都不填；「查配方」時只填關鍵字。
- 比對前，原文和名稱都轉成半形、小寫，去掉空白。
- 英文縮寫和「HQ」的前後、「Lv」「iLv」的前面，不能緊接英文字母或數字。原文中隔著空白不算緊接：「WHM 90級」的 WHM 算，「whm90級」的不算。

### 模型負責

模型用純文字回答，每個欄位一行「標籤：值」，搭配寬鬆的 guardrail（`permissiveContentTransformations`）。
第三輪有一般句子被 guardrail 擋下；Apple 文件說寬鬆的 guardrail 只對純文字回答有效，用 schema 時和預設一樣會擋，所以不用 schema。

```
用法：搜尋
關鍵字：歐米茄
```

- 標籤是「用法」「關鍵字」，後接全形或半形冒號；標籤前後的空白和 Markdown 符號（- * #）、值前後的空白和引號去掉。其他行忽略，同一個標籤只看第一行。
- 沒有關鍵字時省略那一行；值是空白、「無」或「沒有」也代表沒有。
- 沒有用法那一行，或用法不是下列三種之一時，整個回答無法讀取（包括模型回的拒答訊息）。

- **用法**：搜尋／查配方／無法處理。
  - 搜尋：用條件或名稱找道具。
  - 查配方：「做 X 要什麼材料」「X 怎麼做」。
  - 無法處理：描述用途或效果的查詢、跟道具無關的句子。
- **關鍵字**：道具名稱的一部分。只能從原文擷取，不補全、不翻譯、不改寫。查配方時就是那個道具的名稱。程式再檢查：
  - 不在原文裡的關鍵字丟掉；
  - 扣掉比對到的條件和連接條件用的字（的、裝備、能穿…）後什麼都不剩的關鍵字丟掉（例：「頭部裝備」「繪靈法師的筆」），
    但關鍵字就是 `items.json` 裡某個道具的完整名稱（照原樣比對），又不只是一個條件的名稱時保留（例：「紅蓮盾」保留，「毒蛇」「天球儀」仍是條件）；
  - 留下的關鍵字是道具名稱，落在它裡面的條件不算（例：「守護者之盾」的「盾」不算分類）。

### 程式比對

- 分類、部位、職業、稀有度的名稱整段比對原文：
  - 名稱互相重疊時取最長的，被包含的不算。「龍騎士」不會再對到「騎士」，「武士刀」不會再對到「武士」，「採掘工具」不會再對到「採掘」。
- **分類**：`items.json` 的 112 個分類名稱。用於武器、工具的種類（例：雙手幻杖）、盾、靈魂水晶，以及非裝備道具（例：藥品、食材）。
  - 名稱有括號的分類，原文不寫括號也算（「採掘工具主工具」→ 採掘工具（主工具））。
  - 只寫括號前或括號裡的部分時，對到所有符合的分類（「採掘工具」→ 採掘工具的主工具和副工具；「副工具」→ 所有副工具）。
    這個部分本身也是分類名稱時，連同它一起（「魔導書」→ 魔導書和魔導書（學者專用））。
    句子裡有職業時，只留那些職業能用的分類（「鍊金術師的副工具」→ 鍊金工具（副工具））；職業都用不到時全部保留。
    職業能用的分類從 `items.json` 的道具算出。
- **部位**：主手、副手、頭部、身體、手部、腿部、腳部、耳部、頸部、腕部、戒指，共 11 個。
  - 防具和飾品的分類，解析時換成對應的部位（例：「頭部防具」→ 頭部、「耳飾」→ 耳部）。
    換的是「可裝備的道具全部裝在同一個部位，而且不是主手或副手」的分類，從 `items.json` 算出；
    盾、武器、工具的分類維持分類。
  - 盾用分類「盾」，不用部位「副手」；靈魂水晶用分類，不算部位。
  - 部位是 `items.json` 裝備部位名稱中不含「（」的那些，扣掉靈魂水晶。
  - 對回 id 時，包含「（無法裝備…）」的變體。例如「身體」包含「身體（無法裝備頭部）」等 6 種。
- **職業**：App 職業 filter 的 32 個縮寫。玩家的叫法都要對到同一個縮寫：
  - 官方名稱：讀 `items.json` 中只含單一職業的職業分類（例：白魔道士）；
  - 常用簡稱：寫在以縮寫為 key 的別名表（例：白魔、WHM），key 只能是 App 職業 filter 的縮寫；
  - 不收 App filter 上顯示的名稱（例：白魔法師）。
- **裝備等級範圍**：
  - 「80 級」「等級 80」「Lv.80」= 80–80；後面接「以上」= 80–100，接「以下」「以內」= 1–80；
    「70 到 80 級」「等級 70 到 80」（到、至、~、-）= 70–80。
  - 數字整個比對，「700」不會被當成「70」；隔著空白的是兩個數字。
  - 前面沒有「等級」「Lv」、後面也沒有「級」的數字不算。
- **品級範圍**：數字前面是「品級」「iLv」「裝等」時才是品級，寫法同上，「品級 X 以上」= X–795（App filter 的上限）。其他的一律視為裝備等級。
- 同一句有兩個裝備等級（或兩個品級）時，用第一個。
- **稀有度**：固定 5 個值：1 一般（白）、2 稀有（綠）、3 貴重（藍）、4 武勳（紫）、7 紅蓮（粉）。
  原文寫名稱，或顏色加「色」「裝」（例：紫色、綠裝）。
- **HQ、可交易**：原文有「HQ」就有 HQ 條件；有「交易」「買賣」「市場板」就有可交易條件。
  同一個子句裡（以標點和「又」「但」分隔）、前面四個字內有「不」「無」「沒」「非」「禁」時是否定（例：「不能交易」= 只要不可交易），
  否則是肯定（例：「可以 HQ」= 只要可 HQ）。同一句提到好幾次時，有一次是否定就是否定（「市場板上不能買賣」= 只要不可交易）。

## 評估集

- 每句包含編號、所屬類別、原文和預期的解析結果。
- 至少 41 句（下列組成加總），組成：
  - 組合條件（兩個以上條件）20 句；
  - 裝備等級 5 句、品級 3 句；
  - 查配方 5 句；
  - 名稱裡有可能被 guardrail 擋下字眼的道具 5 句（例：刀、死、血），用 `items.json` 裡真的有的道具；
  - 無法處理 3 句；
  - 職業用簡稱或別名，散在上面各類裡。
- 初稿由實作者寫，使用者確認後定稿。

## 評估工具

- 輸入：`items.json` 和評估集。
- 每句用新的 session，取樣固定，同樣的輸入得到同樣的輸出。
- 輸出：
  - 用法、各欄位的正確率，以及整句完全正確的比例；
  - 錯誤清單：每句的預期與實際；
  - 被 guardrail 擋下和其他錯誤分開計數，各自列出是哪幾句；無法讀取的回答算其他錯誤，並列出模型的回答；
  - 平均耗時，只供參考，Mac 的速度不代表手機；
  - 環境：macOS 版本、日期。
- 模型不可用時（Apple Intelligence 未開啟、模型未下載、裝置不支援、不支援繁中），說明原因並以非 0 結束。
- 評估跑完就以 0 結束，包括有句子被擋或出錯時。只有模型不可用、輸入檔案有誤時以非 0 結束。
- 正確率的算法：
  - 比對前先把名稱對回 id 或縮寫，多選欄位不計順序；
  - 每個欄位只算「預期或實際有值」的句子，兩邊都空的不算進去；
  - 被 guardrail 擋下或出錯的句子，在預期有值的欄位都算錯（用法每句都有值，所以一定算進去）；
  - 整句完全正確的比例以全部句子為分母。
- 檢查模式檢查：
  - 每句的格式，以及編號不重複；
  - 用法是三種之一；
  - 分類、部位、職業都是清單裡的名稱或縮寫；
  - 範圍的下限不大於上限，且在 1–100（裝備等級）、1–795（品級）之內；
  - 關鍵字出現在原文裡。
  - 有錯時指出句子的編號和原文。

## 繼續做 App 的門檻

用法 ≥ 90%、關鍵字 ≥ 90%、其他欄位各 ≥ 85%。
沒達標時，在結果文件記錄原因，由使用者決定調整後重跑，或停止這個功能。
