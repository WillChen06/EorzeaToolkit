## 驗收

**這一節在 Codex 開工前就要寫定。** 它是實作者與驗證者共用的契約 —— 如果等實作完再補,
條件會不自覺地照著已經做出來的東西寫,驗證就退化成自我評分,整條流程的意義就沒了。

實作過程若發現某條驗收條件本身有誤,**改這一節,並在 PR 說明改了什麼、為什麼**。
默默做成別的樣子是 review 的 finding。

每條的要求:

- 可否證。「正確顯示」不算條件,「`in_gil_shop` 不為 true 時商店區塊不顯示」才算。
- 單一行為。一條驗一件事,不要用「且」把三件事綁在一起。
- 不含實作方式。條件描述行為,不指定用哪個型別或哪支函式達成。
- 標上編號與驗證途徑。編號讓 PR 與 review 能逐條對照。

驗證途徑三選一:

| 標記 | 意義 |
| --- | --- |
| `[自動]` | 有 unit test 或 `scripts/validate_data.py` 能證明。已經有對應測試就寫出名稱。 |
| `[diff]` | 讀 diff 就能確認,不必跑起來。 |
| `[人工]` | 必須跑 app 才能確認。這類條件由人確認,review 不會宣稱驗過。 |

範例（取材自道具 detail page,僅示意格式）:

- **AC-1** `[自動]` `in_gil_shop` 為 true 時,該道具視為可在商店購買 ——
  `ItemShopEntryTests.testPriceWithShopFlagIsAShopPurchase`
- **AC-2** `[自動]` 只有 `price_mid` 而無 `in_gil_shop` 時,不視為商店購買
  (那是 NPC 收購價) —— `ItemShopEntryTests.testPriceWithoutShopFlagIsNotAShopPurchase`
- **AC-3** `[diff]` 新增的使用者可見文字全部走 `Localizable.xcstrings`,view 內無硬編字串。
- **AC-4** `[人工]` 來源數 ≥ 2 的道具,detail page 顯示「取得方式」目錄。
- **AC-5** `[人工]` 來源數 ≤ 1 的道具,目錄整塊不 render。
- **AC-6** `[人工]` 點擊目錄項會捲動到對應區塊。
